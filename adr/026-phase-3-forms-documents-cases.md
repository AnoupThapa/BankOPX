# ADR-026 — Phase 3 forms, documents and the first case states
**Status:** Accepted (Phase 3); storage product, scan engine and retention are **Bank-decides**
**Date:** 2026-10-29
**Context:** Implements FRM-01..07/09..12, DOC-01..09/11/12, RET-01..05, SUB-01/02/04 on top of ADR-024/025. The workflow engine (ADR-018) is not built until Phase 4.
**Decision:**
1. **Forms are a configuration kind (`form`)** with a typed field schema. The server validates every submission against the version the draft or case is pinned to; errors are codes, wording is localised by the client. The server never rewrites a value: unknown fields, values for hidden fields and mismatched calculated values are errors, and tidying (for example trimming) is returned as a suggestion only (FRM-05). Calculated fields use a small closed set of operations with a visible formula and version; there is no expression evaluator.
2. **Publication is blocked by a regression pack** for forms (privacy class, translations, reachable conditions, formula version, file field settings, risky regular expressions, nesting and size limits) and a dry-run endpoint lets designers see blockers before review.
3. **A draft pins its form version on first save**, and a case pins the version it was submitted on. Retired versions stay readable to the work that pinned them.
4. **Submission is one transaction**: consume the draft, validate, create the case with a random tracking code, write snapshot 1, attach documents, record the first transition. Idempotency keys make a retry return the same receipt. A resubmission writes snapshot N+1; earlier snapshots are never changed (database triggers).
5. **Case state moves only through one function** (a database trigger refuses any other change), with an append-only transition record (actor, reason, prior and new state) and an audit event; invalid moves are rejected and audited. This is a deliberately tiny seed (submitted, returned to customer, resubmitted). Phase 4 replaces the table with the versioned engine and keeps the record format. The customer sees only the controlled status dictionary.
6. **Documents** arrive as the raw request body (no multipart parser). Type is decided by the file's signature, must agree with the declared type and extension, and a conservative set of active-content markers is refused. Bytes are encrypted (AES-256-GCM) into a private object store port; the database keeps only the key, SHA-256, size and type. Scan status starts `pending`; staff can read only `clean`; a scanner outage leaves files pending and a missing scanner is the default. Infected files are kept quarantined and unreadable. Versions are immutable except the one-way scan result. Every read, download and link is an access event and an audit event. Reads verify the hash. The reviewer cannot be the uploader.
7. **Short-lived signed links** are bound to one user and one version, expire in 60 seconds by default, and still require that user's session and a fresh permission check.
8. **Staff access is scoped by the case's branch**, taken from the customer's home branch at submission. Lists are filtered in the query; out-of-scope ids look absent. A case with no branch is visible to no one until Phase 4 routing exists.
9. **Audit hashing is canonical**: object keys are sorted before hashing, because Postgres `jsonb` does not preserve key order. (This fixes a Phase 1 defect, see the report.)
**Consequences:** Mandatory documents cannot be forced to a stage other than "before submission" yet (DOC-13 is enforced at submission only). Resumable chunked upload is not built; retries are safe through idempotency keys. The first case states are limited, so reviewing, approving and closing arrive with the engine.
**Alternatives considered:** multipart upload library (known vulnerabilities in this dependency family, larger attack surface); an expression language for calculated fields (code-injection risk); building the full engine now (premature without the Phase 4 spike).
