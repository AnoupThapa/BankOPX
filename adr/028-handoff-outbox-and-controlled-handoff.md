# ADR-028 — Hand-off to the authoritative system: outbox, one connector port, controlled hand-off first
**Status:** Accepted for Phase 5, **pending review by the tech lead and the bank's integration owner**; refines ADR-017
**Date:** 2026-10-29
**Context:** INT-01 says fulfilment is complete only when the authoritative system confirms. INT-02..04 require idempotency keys, bounded retries, dead letters, visible ambiguity and safe retry. The first pilot has no agreed bank API (docs/18 allows "one bank system or controlled hand-off"; docs/09 §6 allows a file exchange). We must not assume an API, a vendor or an authorisation we do not have (docs/09 §7).
**Decision:**
1. **Outbox row in the decision transaction.** When a workflow ends in `approved` and the pinned service version carries a `fulfilment` block (`connector`, `operation`), one `integration_request` row is inserted in the same transaction as the decision. A unique key on (institution, case, operation) makes a replay harmless. Declined cases and services without the block create nothing.
2. **One port, many adapters.** `FulfilmentConnector` (`dispatch`, optional `status`) is the only thing business code knows. Adapters are registered by key. The pilot ships `ControlledHandoffConnector`, which accepts the request and waits: nothing is executed by the platform.
3. **Confirmation is a separate, authenticated event** with the system of record's reference: (a) the connector says so synchronously, (b) an HMAC-signed callback, or (c) an authorised operator records the bank's reference with a note. The database refuses `confirmed` without a reference, a method and a time, and refuses any later change.
4. **Dispatcher** claims due rows with a lease (`SKIP LOCKED`), calls the connector outside any row lock, then applies the outcome: accepted → `sent`; definite not-executed → bounded retry with backoff, then `dead_letter`; definite refusal → `failed`; timeout or exception → `ambiguous`. Provider error text is never stored, only a short code.
5. **Ambiguous is never retried blindly.** An operator resolves it (ask the system, or record a finding) and only then retries, with the same idempotency key.
6. **The customer sees three states only:** not applicable, in progress, completed. Everything but `confirmed` is "in progress".
7. **Case state is not changed by fulfilment.** The case stays `approved` (the human decision). Fulfilment is its own record and lifecycle, so a failed hand-off cannot reopen or undo a decision (WFL-05) and no direct status update is needed (WFL-03).
**Consequences:** fulfilment status needs one more read for the customer view. At-least-once delivery means any real connector must dedupe on the idempotency key (documented in the connector contract). The scheduler is optional (`BBJP_SCHEDULER=1`); without it an operator or the integration identity triggers dispatch.
**Not decided here (needs the bank):** which connector replaces the controlled hand-off; file exchange format and key exchange; callback secret management; reconciliation frequency; who may confirm.
**Alternatives rejected:** calling the bank inline from the approval request (loses requests, violates ADR-017); marking the case "completed" when the request is sent (violates INT-01); a new case state per fulfilment step (couples decisions to integrations).
