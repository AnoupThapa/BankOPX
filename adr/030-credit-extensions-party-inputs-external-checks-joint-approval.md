# ADR-030 — Credit extensions: per-party inputs, external checks through a port and outbox-style dispatch, joint approval tiers
**Status:** Accepted for Phase 6b, **pending review by the tech lead and the credit policy owner**
**Date:** 2026-10-29
**Context:** Phase 6a (ADR-029) left four gaps: inputs only at proposal level (A-040), no external checks (A-038), only per-person approval limits (A-039), and overdue conditions that nobody saw (A-041). The bank has still not supplied definitions, providers or an authority matrix.
**Decision:**
1. **Per-party inputs.** A calculation-set input may have `scope: "party"` with `partyRoles` and `aggregate` (`sum`, `max`, `min`). The figure a measure uses is the combination of the counted parties' latest values. A counted party with no value makes the figure missing; a contested value contests it; the combined date is the oldest contributor. Worked examples state the combined figure. Periods are not modelled.
2. **External checks** use `ExternalCheckPort` (default: unconfigured, always "unavailable"). A service lists the providers it may use (`credit.externalChecks`). A request needs a lawful basis, consent evidence, an authorised provider and a party, and is only **recorded**; the call is made later by a dispatcher run by the integration identity or the scheduler (CLAUDE.md §4, ADR-017). The table is append-only, each step is a row, the latest row per correlation ID is the state. The subject (the party's name) is read at dispatch time and passed to the provider for that call only. A result is a reference and bank-defined summary fields, never a report. A check that was sent but has no result is shown as such; it is not re-sent.
3. **Joint approval** is a workflow approval-node setting `jointApproval: [{ aboveAmount, approvals }]` (strictly increasing thresholds, 2 to 5 approvals, non-decreasing). An amount above a threshold needs that many different approvers. Each must individually pass the authority checks (limit, branch, separation from earlier stages). A partial approval is recorded in `approval`, the task returns to the queue unassigned, and the case does not move; the hand-off exists only after the last approval. One decline by an authorised approver ends the request. An unknown amount needs the highest tier. The engine does not model committees, quorum or alternates.
4. **Overdue conditions** are flagged once (audited) by the dispatcher and counted on a portfolio view. No task, notification or escalation is raised because ownership of overdue work is a bank decision (A-041 stays open).
5. **Portfolio** is counts only for the viewer's branches, with definitions.
**Consequences:** The decimal helper moved to the platform module so workflow and credit share one implementation. Case state for portfolio counts comes from `CaseService.statesOf` (no cross-module joins). Dispatching external checks takes an advisory lock instead of row locks because the application role has no UPDATE right on append-only tables.
**Not decided (bank):** which providers, what summary fields mean, thresholds and approval counts, whether a joint approval needs a particular role mix, who owns overdue conditions.
**Alternatives rejected:** calling the provider inside the officer's request (violates ADR-017 and ties request latency to a third party); storing the provider's report (data we do not need and may not hold); counting joint approvals by role only (allows one person with two roles to approve twice).
